# CUDA 对齐类型与访存吞吐量：alignedTypes

本文以 CUDA Samples 的 `alignedTypes` 示例为基础，说明数据结构的对齐（alignment）如何影响 GPU 全局内存访问效率，以及如何通过对照实验观察这种影响。

本示例不是通用的结构体性能基准，也不能据此推断所有 GPU、编译选项或数据布局下的固定提升比例。它的重点是：在相同拷贝 Kernel、相同数据规模和相同线程配置下，只改变元素类型的布局，对比对齐类型与非对齐类型的访问吞吐量。

## 1. 示例演示什么

`alignedTypes` 对一块较大的 GPU 缓冲区执行逐元素拷贝，并分别测试：

- 未显式声明对齐的结构体；
- 使用 `__align__(4)`、`__align__(8)` 或 `__align__(16)` 声明对齐的结构体；
- 元素大小为 1、2、4、8、12、16 和 32 字节的类型。

它关注的是**结构体元素的对齐和大小是否适合 GPU 全局内存访问**。当线程按元素读取和写入连续数组时，元素的起始地址、元素跨度以及编译器生成的加载/存储指令都会影响全局内存事务和实际吞吐量。

这里的“对齐”不是简单地把数据填充到更大的尺寸，而是让对象的起始地址满足指定边界，并使编译器能够按适合硬件的宽度访问数据。

## 2. 示例如何实现

### 2.1 定义两组类型

源码定义了非对齐类型，例如：

```cpp
typedef struct {
  unsigned int r, g, b;
} RGB32_misaligned;
```

以及显式对齐类型：

```cpp
typedef struct __align__(16) {
  unsigned int r, g, b;
} RGB32;
```

示例还测试 `RGBA8`、`LA32`、`RGB32`、`RGBA32` 等类型，并用 `_misaligned` 后缀区分未显式对齐的版本。

需要注意，`__align__` 只指定对象的对齐要求，不会自动消除所有访问成本。结构体大小、数组步长、实际字段布局和编译器生成的指令都必须一起考虑。

### 2.2 使用同一个拷贝 Kernel

所有类型都通过同一个模板 Kernel 测试：

```cpp
template <class TData>
__global__ void testKernel(TData *d_odata, TData *d_idata, int numElements) {
  const int tid = blockDim.x * blockIdx.x + threadIdx.x;
  const int numThreads = blockDim.x * gridDim.x;

  for (int pos = tid; pos < numElements; pos += numThreads) {
    d_odata[pos] = d_idata[pos];
  }
}
```

Kernel 让每个线程以步长 `gridDim.x * blockDim.x` 处理多个元素。测试启动配置固定为：

```cpp
<<<64, 256>>>
```

这样可以尽量把变量集中在 `TData` 的类型布局，而不是改变算法或线程组织。

### 2.3 对每种类型重复测量

每种类型都执行以下步骤：

1. 根据 `sizeof(TData)` 计算可完整容纳的元素数量；
2. 清空输出缓冲区；
3. 调用 Kernel 32 次；
4. 使用 CPU 计时器测量总时间，再计算平均每次拷贝时间；
5. 将结果从 GPU 拷回主机并进行校验。

测试使用约 50,000,000 字节的内存块；对于较低计算能力的设备，程序会根据 SM 数量缩小工作量。内存大小还会调整为 256 字节的整数倍。

## 3. 为什么要比较对齐与非对齐类型

GPU 全局内存访问通常以内存事务为单位完成。一个 Warp 的线程如果访问连续且适当对齐的地址，硬件更容易用较少的事务满足整个 Warp 的请求；如果元素起始地址或访问宽度不理想，可能产生更多事务、拆分加载/存储，或生成效率较低的指令序列。

对齐良好的数据布局通常有以下优势：

- 数组元素的起始地址满足硬件访问要求；
- 编译器更容易生成合适宽度的加载和存储指令；
- Warp 访问连续元素时，更容易形成高效的合并访问；
- 减少因跨越事务边界而产生的额外内存事务。

但对齐并不保证一定更快。实际结果还取决于：

- 元素大小是否为硬件支持的自然访问宽度；
- 结构体是否包含填充字节；
- 数组总大小和起始地址；
- GPU 架构、编译器和缓存状态；
- 测试是否已经受显存带宽或其他因素限制。

## 4. 为什么 12 字节和 32 字节类型需要特别注意

示例源码说明，硬件对 4、8、16 字节的数据元素通常有更直接的全局内存访问支持。即使声明了 `__align__(16)`，超过 16 字节的结构体也可能需要多条加载或存储指令。

因此，`RGBA32_2` 虽然声明为 16 字节对齐，但实际大小为 32 字节：

```cpp
typedef struct __align__(16) {
  RGBA32 c1, c2;
} RGBA32_2;
```

这并不意味着它可以像单个 16 字节元素一样由一条访问完成。对于较大的复合数据，源码注释建议一般情况下考虑“数组结构”（Structure of Arrays，SoA）布局，而不是把多个字段打包到一个很大的结构体中。

两种常见布局如下：

```text
数组结构（SoA）：r[...], g[...], b[...], a[...]
数组中的结构体（AoS）：{r, g, b, a}, {r, g, b, a}, ...
```

选择哪种布局应由实际 Kernel 的访问模式决定。若同一个 Warp 同时处理同一字段的连续元素，SoA 往往更容易形成合并访问；若线程总是需要同一元素的全部字段，AoS 可能更自然。

## 5. 如何观察测试结果

程序对每种类型输出平均耗时和拷贝吞吐量，形式类似：

```text
Avg. time: <平均毫秒数> ms / Copy throughput: <吞吐量> GB/s.
```

源码中的吞吐量计算近似为：

```text
吞吐量（GB/s）= 实际参与拷贝的字节数 / 平均时间（秒）/ 2^30
```

这里的 `GB/s` 实际使用 `2^30` 作为换算因子，更接近 GiB/s；它是本示例定义的有效拷贝吞吐量，不等于显存物理带宽，也不代表端到端应用吞吐量。

比较结果时应重点观察：

- 同一类型多次运行的耗时是否稳定；
- 对齐类型与对应非对齐类型的吞吐量差异；
- 元素大小改变后，吞吐量是否发生变化；
- `TEST OK` 是否出现；
- 最终是否输出 `Test passed`。

## 6. “提升有多少”应该如何计算

对一组对应的非对齐类型和对齐类型，可使用以下公式：

```text
吞吐量提升百分比 =（对齐吞吐量 - 非对齐吞吐量）/ 非对齐吞吐量 × 100%
耗时下降百分比 =（非对齐耗时 - 对齐耗时）/ 非对齐耗时 × 100%
```

例如，若非对齐版本为 500 GB/s，对齐版本为 600 GB/s，则吞吐量提升为：

```text
（600 - 500）/ 500 × 100% = 20%
```

但不要预先写死一个“对齐一定提升多少”的结论。这个示例的目的在于展示潜在的显著差异，具体提升比例必须以同一设备、同一构建条件和同一运行环境下的实际输出为准。某些类型在当前 GPU 上可能差异很小，甚至由于缓存、测量误差或其他因素出现反向结果。

另外，示例中的“对齐类型”和“非对齐类型”并不总是严格的一一对应性能实验。例如 `RGBA8_misaligned` 与 `RGBA8` 的字段大小相同，而 `RGB32_misaligned` 与 `RGB32` 的区别主要是显式对齐声明；`RGBA32_2` 则是更大结构体的单独测试，不能直接与某个 16 字节类型比较提升百分比。

## 7. 正确性校验说明

GPU 拷贝完成后，程序将输出拷回主机，并与输入数据比较。比较时只检查结构体中实际字段组成的“紧凑数据区域”，不比较编译器插入的填充字节。

这是因为填充字节不是用户字段，其内容不应被当作业务数据；编译器对填充字节的处理也不应作为本示例的正确性判断依据。

如果所有测试通过，程序最后输出：

```text
Test passed
```

## 8. 如何构建和运行

先按照 [CUDA 示例编译指导](00_CUDA示例编译指导.md) 完成构建，然后从仓库根目录运行：

```bash
(cd build/Samples/6_Performance/alignedTypes && ./alignedTypes)
(cd build/Samples/6_Performance/alignedTypes && ./alignedTypes -device=0)
```

程序会自动选择设备并打印设备名称、SM 数量、缩放因子、测试类型、平均耗时、吞吐量和校验结果。示例没有提供用于调整内存大小或迭代次数的命令行参数；如需改变实验条件，应在源码中修改 `MEM_SIZE` 或 `NUM_ITERATIONS` 后重新编译。

## 9. 建议的动手实验

1. 在同一块 GPU 上运行多次，记录每种类型的平均耗时和吞吐量。
2. 对比 `RGB32_misaligned` 与 `RGB32`、`RGBA32_misaligned` 与 `RGBA32`。
3. 计算每组类型的吞吐量提升百分比和耗时下降百分比。
4. 修改 `MEM_SIZE`，观察小数据量下计时稳定性和吞吐量变化。
5. 修改线程块配置，观察线程组织变化是否影响不同元素大小的结果。
6. 进一步比较 AoS 与 SoA 数据布局，验证数据布局是否符合实际访问模式。

本案例通常不需要 Nsight 才能得到“哪个类型更快”的结论。CUDA Samples 输出的平均耗时和有效吞吐量已经足够完成基础对比；只有在需要解释具体的内存事务、加载指令或缓存行为时，才适合进一步使用性能分析工具。

## 10. 与学习路线的关系

`alignedTypes` 适合放在 `transpose` 之后、`matrixMul` 之前作为访存布局补充案例：

- `transpose` 重点展示全局内存合并访问、共享内存和存储体冲突；
- `alignedTypes` 重点展示元素对齐、结构体布局和访问宽度；
- `matrixMul` 再把这些访存基础扩展到分块、数据复用和计算吞吐优化。
